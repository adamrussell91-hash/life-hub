# Cognitive protocols in Knowledge Hub

## Approved outcome
Add a first-class Cognitive protocols destination to the current consolidated `apps/knowledge` app. Eight interactive protocols use the original Notion architecture and voices. Cards arrive from the edges, flip, step forward to speak and retreat when another speaker takes the floor. The visual language remains the shared hub kit: Inter, existing closed palette, cotton surfaces and navy rail. Motifs are subtle line art drawn from the actual source: Greek threads (Fates), Norse hall/horizon (Horizon Council), chevruta paired argument (Refinery), mapping (Cartographers), Confucian rectification/reflection (Mirror Council), Roman/medieval advisory chamber (Consilium), Zen/Vipassana spaciousness (Witness) and nested frames/scale (Tribunal). Do not invent a cultural attribution where none is in the source.

## Protocol fidelity
Port source-specific prompts faithfully; separate AI calls per named voice, with controller-owned stage transitions. Keep authentic speech rhythms and boundaries. Controller directions never become an extra analytical opinion. State persists on the server, including evidence, turns, question checkpoints and corrections. A reload can resume. Tribunal voices receive the same original input and cannot see one another. Consilium is adaptive live dialogue, with Virtue never first and a final user reflection that is not analysed. Witness cannot identify patterns before the user verifies the trace. Fates pauses after questions and follows its selected sprint/normal/long structure. Mandatory intake fields cannot be bypassed by model suggestions. Implement source modes for all eight protocols.

Sources are the eight original pages and backend specification, exported privately under `/private/tmp/knowledge-cognitive-source`. Those exports are reference material, not repo assets. Do not commit personal biographical context, sensitive examples or raw Notion exports. Prompts should carry the source's generic rules, with user context supplied at runtime.

Retrieval must use actual Knowledge Hub notes first. Label evidence gaps, self-report and trained knowledge; never pretend a search happened. No fabricated quotations or links. Optional web lookup must be an actual tool if offered. Read-only evidence retrieval is within scope; no automatic archive/memory writes, cross-hub actions or handoffs. Offer a reviewable explicit Save session action through the existing Knowledge Hub save flow, and a local transcript download. Persisting a session itself is authorised by starting it.

## Runtime and accessibility
Use current Netlify authentication, provider and durable storage conventions. Model calls run in background functions with polling, keeping expensive generation out of synchronous request deadlines. Authorise every read/write, keep owner binding stable within authenticated identity, validate IDs/actions/limits, prevent duplicate actions and concurrent advances with durable compare-and-set. Handle failures visibly with retry that cannot duplicate completed voice turns. No browser API keys or authoritative client-supplied transcript/state. No production schema migrations or live deployment in this feature task.

Reuse shared motion/card primitives where they fit. Keyboard-operable cards and controls, focus management, reduced motion and responsive layout are required. Do not animate an entire long response or hide essential text behind motion. Protocol selection/intake/history should be useful with the live API unavailable; preview must clearly distinguish any simulated responses.

## Verification
Meaningful deterministic controller and API tests: all eight paths/modes, required input, question gates, Tribunal isolation, Witness verification/correction, Consilium sequencing, cancellation/retry, authentication/ownership and duplicate/concurrent actions. UI tests cover selection, keyboard, request failure/retry, resume and disposal. Run applicable existing tests and production build. Inspect desktop/mobile/reduced-motion interface. Create a voice fidelity evaluation guide with representative inputs, expected differences and exact limitations of deterministic tests. Do not claim live voice fidelity without actual model samples.
